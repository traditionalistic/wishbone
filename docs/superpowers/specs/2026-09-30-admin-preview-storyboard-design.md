# Превью и сториборд в админке — дизайн

> Статус: **дизайн 2026-09-30**. Дополняет [спеку V1](2026-09-27-wishbone-v1-design.md) §5.4 (превью) и §7 (админка). Веб-рендер по-прежнему вне объёма (§0, §8.3): картинки в админке рисуют настоящие SDK на подключённых устройствах.

## 0. Цель и объём

1. **Превью экрана.** В админке рядом с редактором стоят два телефона, iOS и Android, с отрендеренным текущим исходником (несохранённым тоже). Картинка обновляется через 1–1,5 с после правки.
2. **Сториборд.** Вкладка **Board** показывает все экраны, связанные с открытым через `navigate`/`present` в обе стороны: карточки со снимками iOS и Android и стрелки переходов. Клик по карточке открывает экран в редакторе.
3. **Устройства не отваливаются.** Сессия превью живёт столько же, сколько вкладка админки, а не один экран. Устройство выбирает код один раз и дальше следует за админкой.

Вне объёма: веб-рендер, рендер без подключённого устройства (кэш снимков, воркеры-демоны, JVM-рендер Android), переключатель «черновики / опубликованное», динамические цели `navigate(expr)`, выбор темы и локали для снимка, полная высота прокрутки (снимок — первый экран).

## 1. Модель

Снимки делают устройства, подключённые к сессии превью: симулятор, эмулятор или телефон с плейграундом. Сервер Linux ничего не рисует. Он компилирует экраны, решает, что и на каком устройстве перерисовать, хранит последние снимки сессии в памяти и отдаёт их админке. Устройство отвечает на задание `render` ровно одним `shot`.

### 1.1 Сессия на вкладку

- `usePreview(source)` создаёт сессию один раз на вкладку. Код лежит в `sessionStorage` и переиспользуется после перезагрузки, пока `GET /v1/preview/sessions` его показывает. На потерю сессии (404) хук пересоздаёт её, как сейчас.
- Смена экрана — обычный `POST …/document` с исходником другого экрана. `Hub` уже переводит сессию на `screen` из документа.
- SDK: живой документ с другим `screen`, чем у текущего, строит новый `Store` без переноса значений state. Перенос по имени остаётся только для правок того же экрана.

### 1.2 Граф переходов

Компилятор собирает ссылки тем же обходом, которым `meta()` собирает `Meta.Ops` (тела обработчиков и `on` узлов, с заходом в `if`/`anim`):

```go
// Link — переход экрана: `navigate`/`present` с литералом-целью (["v", id]); динамические цели пропускаются.
type Link struct {
	To   string `json:"to"`
	Kind string `json:"kind"` // "navigate" | "present"
	Via  string `json:"via"`  // "node:<id>" | "handler:<name>"
}
// Meta.Links []Link — без дублей, отсортированы по (To, Kind, Via)
```

Проводной вид: `["do","navigate",[["v","raffle.tickets"],…],false]`, `["do","present",[["v","raffle.rules"],…],false]`.

### 1.3 Доска (board)

`board(ctx, focus)` в `backend/internal/api/board.go`:

- Фокус — открытый экран, скомпилированный из присланного исходника. Его сохранённый черновик не используется.
- Остальные экраны — сохранённые черновики из `Store`. Кэш в памяти сервера по `(id, updatedAt)` хранит скомпилированный документ, мету, ссылки и данные, разрешённые один раз с дефолтами параметров. Данные связанных экранов не перезапрашиваются, пока черновик не изменится. `ponytail:` кэш без вытеснения, ограничен числом экранов.
- Состав — компонента связности фокуса по ссылкам без учёта направления, BFS от фокуса, не больше 16 экранов (`maxBoard`, `ponytail:` поднять, когда реальный флоу упрётся).
- Цель ссылки, которой нет в `Store`, попадает на доску «призраком» с `error: "screen not found"` и не рендерится. Черновик, который не компилируется, попадает с `error: "draft does not compile: <первая диагностика>"`, без ссылок, и тоже не рендерится.
- Ошибка `Store` пишется в лог, доска сводится к фокусу: живое превью от сториборда не зависит.

### 1.4 Планировщик (hub)

`Hub.Push(code, Board)` заменяет `SetDocument`:

- Живой документ фокуса уходит всем устройствам, как раньше (`{"type":"document",…}`, `rebase` на хост устройства).
- Для каждого экрана доски хаб считает `hash = sha256(document, data)`. Снимки неизменившихся экранов остаются. Снимки экранов, ушедших с доски, удаляются. Повторный `Push` той же доски не порождает заданий.
- Следующее задание устройства — чистая функция `next(session, peer)`: первый экран доски (фокус первым, дальше порядок BFS) без `error`, у которого нет снимка этого устройства для текущего хеша. Очереди нет. Новый `Push` сам вытесняет старую работу.
- У устройства не больше одного задания в работе. Таймаут задания 15 с, после него снимок `failed: "timeout"`. Проваленный снимок для текущего хеша считается сделанным до `retry` или нового хеша.
- Задания раздаются, только пока сессию смотрит хотя бы одна админка. Подключение админки запускает раздачу.
- Ответ на что-либо, кроме задания в работе, устарел и отбрасывается (идентификатор задания). Если хеш успел смениться, снимок всё равно сохраняется с хешем задания (новая картинка лучше никакой), и `next` сразу ставит новый хеш.
- Уход устройства удаляет его снимки и останавливает таймер задания.
- `Meta(screen)` не меняется: снимки не делают сетевых вызовов (§2.1), им не нужна мета связанных экранов.

### 1.5 Проверка на границе

Сокет устройства не аутентифицирован (только код). Хаб проверяет `shot`: base64 декодируется не больше чем в 1 МиБ, начинается с `FF D8 FF` (JPEG), `1 ≤ width, height ≤ 2000`, строка ошибки обрезается до 200 символов. Иначе снимок `failed: "invalid shot"`. Лимит чтения сокета устройства 4 МиБ (у coder/websocket по умолчанию 32 КиБ, и первый снимок оборвал бы соединение). Админке снимок уходит только как `data:image/jpeg;base64,…`.

## 2. Устройство

### 2.1 Режим снимка

Задание рендерится в слое снимка под живым превью в том же окне: тот же размер экрана, те же safe area, та же схема. Слой не виден пользователю, не принимает касания и скрыт от доступности. Store слоя работает в режиме `capture`:

- state, computed, таймлайны и обработчики `appear` работают;
- `navigate`, `back`, `present`, `dismiss`, `open`, `haptic`, `track`, `host` ничего не делают;
- `call` и `refresh` не уходят в сеть и остаются незавершёнными до разборки слоя. Снимок не пишет на сервер и не зовёт `/v1/call` для чужого экрана.

Параметры экрана — дефолты документа. Данные — из задания.

### 2.2 «Успокоился»

Одно правило на обеих платформах. Первые 700 мс ждём всегда: это покрывает самый долгий токен движения (`slow`, 500 мс) и переходы SwiftUI/Compose, которые счётчики не видят. Потом снимок делается, когда 100 мс подряд (два опроса по 50 мс) нет загрузок картинок в полёте и нет идущих конечных таймлайнов. Бесконечные таймлайны (спиннеры) не ждём. Через 6 с снимок делается в любом случае с `settled: false`. Три числа — ручки калибровки.

### 2.3 Захват

- iOS: слой снимка — `UIHostingController` под живым экраном (`UIViewControllerRepresentable` в `ZStack`), кадр — `drawHierarchy(in:afterScreenUpdates: true)` его view в `UIGraphicsImageRenderer` со scale 2, JPEG с качеством 0,7. `ImageRenderer` не подходит: он не рисует содержимое `ScrollView` и UIKit-вьюхи.
- Android: слой снимка — дочерний элемент `Box` под живым экраном, записанный в `GraphicsLayer` через `Modifier.drawWithContent { layer.record { drawContent() } }` без отрисовки на экран, затем `layer.toImageBitmap()` (аппаратный, рисует аппаратные битмапы Coil), масштаб 2 px на dp, JPEG 70.
- `width`/`height` в ответе — размер в pt/dp.
- Rive (Metal / TextureView) на снимке может быть пустым. Это принято.
- Приложение в фоне отвечает `{"type":"shot","job":N,"error":"app is in the background"}`.

Первое, что делает каждая платформа, — проверка захвата на симуляторе/эмуляторе: экран со `ScrollView`, сетевой картинкой и `textField` даёт непустой JPEG, совпадающий с живым экраном. Если приём из §2.3 не работает, платформа сообщает об этом до остальной работы.

## 3. Протокол (дополнения к contract/api.md)

Устройство → сервер:

```jsonc
{"type": "hello", "platform": "ios", "device": "iPhone 17 Pro", "runtime": "1.1.0", "render": true}
{"type": "shot", "job": 17, "image": "<base64 JPEG>", "width": 402, "height": 874, "settled": true}
{"type": "shot", "job": 17, "error": "app is in the background"}
```

Плейграунды без `render: true` получают живое превью, но не задания.

Сервер → устройство:

```jsonc
{"type": "render", "job": 17, "screen": "raffle.tickets", "document": {…}, "data": {…}}
```

Сервер → админка (существующий WebSocket админки):

```jsonc
{"type": "devices", "list": [{"id": "d1", "platform": "ios", "device": "iPhone 17 Pro", "render": true}]}
{"type": "board", "focus": "raffle.main", "screens": [
  {"id": "raffle.main", "title": "Розыгрыш", "links": [{"to": "raffle.tickets", "kind": "navigate", "via": "node:progress"}]},
  {"id": "raffle.gone", "title": "", "links": [], "error": "screen not found"}]}
{"type": "frame", "screen": "raffle.main", "device": "d1", "status": "rendering"}
{"type": "frame", "screen": "raffle.main", "device": "d1", "status": "ready", "src": "data:image/jpeg;base64,…", "width": 402, "height": 874, "settled": true}
{"type": "frame", "screen": "raffle.main", "device": "d2", "status": "failed", "error": "timeout"}
{"type": "frames", "list": [ /* объекты frame без "type" */ ]}
```

При подключении админки сервер шлёт `devices`, `board` (если есть) и одним сообщением `frames` все хранимые снимки. Очередь пира — 32 сообщения, поэтому повтор по одному сообщению на снимок переполнил бы её на доске 16 × 2.

Новый маршрут: `POST /admin/api/preview/{code}/retry` → 204. Сбрасывает проваленные снимки, их экраны рендерятся заново.

## 4. Админка

- **Колонка Preview** между редактором и инспектором: iOS и Android рядом, каждый в пропорции своего устройства. В слоте — снимок фокуса с выбранного устройства платформы (по умолчанию первое с `render: true`; если устройств платформы несколько, в шапке слота переключатель). Колонку можно свернуть кнопкой в TopBar, состояние в `localStorage`.
- **Вкладка Board** рядом со Script, Timeline и JSON. Раскладка — чистая функция `layoutBoard(board)`: слой карточки — длиннейший путь от истоков компоненты (обратные рёбра DFS не считаются; если истоков нет, исток — фокус), строки — в порядке обнаружения. Раскладка не зависит от фокуса, поэтому доска не прыгает при кликах. Карточка — заголовок, id и снимки iOS и Android рядом. Стрелки SVG: `navigate` сплошная, `present` пунктир. Фокус подсвечен. Клик открывает экран (с тем же подтверждением несохранённых правок). Без библиотеки графов.
- Состояния слота и карточки:

| Ситуация | Показ |
|---|---|
| Нет устройства платформы в сессии | «iOS не подключён. Откройте Playground на iPhone или симуляторе → сессия **K7Q2**» |
| Устройство без `render: true` | «iPhone 17 Pro — старый Playground: обновите, чтобы видеть снимки здесь» |
| Снимка ещё нет, `rendering` | скелет в пропорции устройства, «Рендер на Pixel 9…» |
| `rendering` поверх старого снимка | старый снимок и спиннер в углу |
| `failed` | «Не отрендерилось на Pixel 9: timeout» и кнопка **Retry** |
| `settled: false` | метка «снято в движении» |
| Исходник не компилируется | снимок и метка «последняя удачная компиляция» |
| Экран с `error` на доске | карточка-призрак с текстом ошибки |
| На доске только фокус | подсказка «Свяжите экраны через navigate(…) / present(…)» |

- `mock.ts` (`VITE_MOCK=1`) отдаёт доску и снимки (SVG data URL), чтобы UI собирался без сервера.

## 6. Проверки

- Go: ссылки `raffle.main` (`raffle.invites`, `raffle.tickets` — navigate, `raffle.rules` — present); планировщик хаба (задание на `Push`, устаревший `shot` отброшен, неверный JPEG → `failed`, повтор при входе админки одним `frames`, без админки заданий нет, повторный `Push` без заданий); доска на засеянных экранах (компонента в обе стороны, призрак, ограничение).
- Админка (vitest): `layoutBoard`, `applyFrame`.
- iOS и Android: режим `capture` глушит исходящие эффекты (тест на Store); захват — вручную на симуляторе и эмуляторе (нужно настоящее окно).
- Сквозная: локальный сервер, iOS-симулятор и Android-эмулятор с плейграундами в одной сессии, админка в браузере. Превью обеих платформ появляется и обновляется после правки. Доска `raffle.main` показывает `slot.feed.top → raffle.main → {invites, tickets, rules}` со снимками обеих платформ.

## 7. Риски и открытые вопросы

- Захват слоя под живым экраном — главный риск (§2.3), его проверяют первым.
- Черновики связанных экранов теперь уходят всем устройствам сессии, а не только открытый экран. Сокет устройства по-прежнему защищён только кодом из 4 символов. Для тестового сервера это приемлемо. Перед чем-то публичным нужна аутентификация устройств.
- Две вкладки админки — две сессии, устройство следует за одной.
- Экраны `raffle.*` на снимке показывают анонимное состояние (данные разрешаются без токена пользователя, как в живом превью).
